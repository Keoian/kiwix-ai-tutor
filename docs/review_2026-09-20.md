## Findings, most severe first

### 1. `ResearchEngine.research()` does not accept `keywords` — production tool-call path is broken
- **Where:** `tutor/retrieval/research.py:317` (`def research(self, query, *, budget_tokens=None, deadline_s=None, topic_hint=None)`) vs. callers at `tutor/app/agent_loop.py:215-219` and `tutor/app/research_tool.py:32-36`, both of which call
  `research_engine.research(query, topic_hint=..., keywords=validation.arguments.get("keywords"))`.
- **Why wrong:** the real engine's signature has no `keywords` parameter at all. Every call site in the app layer passes it anyway.
- **Failing scenario:** wire `agent_loop.run_turn` to a real `ResearchEngine` (as production must) and let the model make *any* follow-up `research` call — even with `keywords` omitted, `validation.arguments.get("keywords")` still passes `keywords=None` explicitly — and `research()` raises `TypeError: research() got an unexpected keyword argument 'keywords'`. This is not a corner case: it fires on every second research call and on `research_tool.run_research`, i.e. the primary tool-call path in spec §9.1.
- **Why tests don't catch it:** `tests/test_agent_loop.py:98-99` uses a hand-written fake research engine whose `research()` *does* accept `keywords`, masking the mismatch. No test constructs a real `ResearchEngine` and drives it through `agent_loop`/`research_tool`.
- **Fix:** add `keywords: list[str] | None = None` to `ResearchEngine.research()` and thread it into `_route`/`_process_archive` per spec §7.2 step 1 ("plus the model keywords if present"), or drop the parameter from the two call sites — but the spec (§7.1, §9.1) requires keywords support, so the engine should gain it. Add an integration test that calls `agent_loop.run_turn` / `research_tool.run_research` against a real `ResearchEngine` (fixture ZIM) to prevent this regressing again.

### 2. `keywords` cap (≤3, ≤40 chars each) from spec §7.1/§9.1 is not enforced anywhere
- **Where:** `tutor/tools/schemas.py:127-134` (`validate_tool_call`) only checks that `keywords` is a list of strings; no length cap, no per-item character cap.
- **Spec:** `offline_tutor_spec_v0.3.md` §7.1 — "`keywords` is new: up to 3 short strings... each ≤ 40 characters, sanitized" — and §9.1 — "`keywords` (optional, ≤ 3)".
- **Failing scenario:** a model tool call `{"query": "...", "keywords": ["a"*5000]*50}` passes validation untouched and (once finding #1 is fixed) would be forwarded straight into the retrieval pipeline — 50 unbounded-length strings feeding lexical variant construction, against a spec that promises the model "cannot specify... query-parser operators" scale of input.
- **Fix:** in `validate_tool_call`, reject when `len(keywords) > 3` or any `len(item) > 40`; also sanitize (spec says "sanitized" — currently no stripping/normalization at all).

### 3. Race condition: `ZimWorker` is not thread-safe but `research.py` calls it from a throwaway thread per op
- **Where:** `tutor/retrieval/research.py:114-134` (`_call_worker` spawns a new daemon `threading.Thread` per worker op, running `worker.request(...)`, and simply drops the thread — no join — if the outer `result_box.get(timeout=deadline_s + _QUEUE_SLACK_S)` times out). `tutor/retrieval/zim/worker.py`'s `ZimWorker.start`/`request`/`_terminate_child` (lines 134-206) mutate `self._process`/`self._conn` with no lock at all.
- **Why wrong:** if the abandoned background thread's `worker.request()` call is still in flight (e.g. it is inside `_terminate_child()` mutating `self._process = None` / `self._conn = None`) at the exact moment `_call_worker` returns `None` upstream and the main thread moves on to the *next* `_call_worker(worker, "fetch_entry", ...)` for the *same* `entry`/`worker` (as happens in the `top_paths` loop of `_process_archive`), the main thread's `self.start()` and the orphaned thread's `_terminate_child()` race on the same unlocked instance attributes. This can produce a `self._conn` that is a half-closed/replaced pipe object read from two threads, or a spurious "started" worker whose process was actually just killed by the other thread, i.e. lost/garbled results or a hung `conn.recv()` that never returns (the very hang the deadline exists to prevent).
- **Concrete trigger:** run `research()` against an archive where the fulltext search worker legitimately takes just over its per-op deadline (e.g. a slow disk / large ZIM under I/O pressure) so the background thread from op N is still finishing teardown when op N+1 for the same archive starts — plausible in exactly the "hard deadline hit, worker restarted" path §7.4 describes as the normal recovery mechanism.
- **Fix:** add a lock inside `ZimWorker` (guarding `start`/`request`/`_terminate_child`/`close`), or make `_call_worker` join the abandoned thread with a hard cap before allowing any further use of that `worker` instance, or dedicate a `Lock` per worker in `ResearchEngine._workers` and hold it for the duration of `_call_worker`.

### 4. `_TOP_N_ARTICLES = 8` in `research.py` does not match the spec's "top 6 (cap 10)"
- **Where:** `tutor/retrieval/research.py:48` — `_TOP_N_ARTICLES = 8`, hard-coded, not one of the "five knobs exposed in config."
- **Spec:** §7.2 step 4 — "Top 6 articles (cap 10)." and step 2 lists "hits per query, articles extracted, passages in packet, evidence budget, and soft deadline" as the five config knobs — articles-extracted should be configurable, not a private module constant.
- **Impact:** not a crash, but it is an undocumented, untested deviation from the number in the spec and it is not one of the five knobs the plan requires to be exposed via config. Either the spec number should be adopted (6) or the deviation needs to be justified in `docs/retrieval_baseline.md` per plan §10.8's "a flag is enabled only by a commit that includes its eval table" spirit (this isn't a ranking flag, but the same evidentiary bar should apply to changing a spec-stated cap).
- **Fix:** either set `_TOP_N_ARTICLES = 6` (and expose it via config, e.g. `ResearchEngine.__init__` parameter, per the "five knobs" requirement) or record the rationale for 8 in `docs/retrieval_baseline.md`.

### 5. No soft-deadline (3 s) distinct from hard-deadline (8 s) — spec §7.4 partially unimplemented
- **Where:** `tutor/retrieval/research.py:51-53` only defines `_DEFAULT_HARD_DEADLINE_S = 8.0` and `_PER_OP_DEADLINE_CAP_S = 3.0` (a *per-op* cap, not a whole-request soft deadline). `ResearchEngine.research()` (line 317) takes a single `deadline_s` and there is no code path that, at 3 s elapsed, proactively returns `partial` while letting the worker keep running in the background as the spec's two-tier design implies — it only ever waits until the 8 s hard ceiling (or per-op remaining time) is exhausted.
- **Spec:** §7.4 — "Soft deadline 3 s, hard 8 s... the app kills the worker at the hard deadline, returns completed stages as `partial`." The 3 s value is meant to be an independent trigger, not just the per-op cap coincidentally reused at 3.0.
- **Impact:** likely benign in practice since `_PER_OP_DEADLINE_CAP_S` happens to equal the spec's soft-deadline number, but this looks like the two concepts were collapsed into one constant rather than deliberately implemented as two, and there's no test (`tests/test_research.py`) asserting a whole-turn soft-deadline behavior distinct from the hard one.
- **Fix:** either document that `_PER_OP_DEADLINE_CAP_S` intentionally realizes the "soft deadline" concept per-archive rather than per-request (and rename/comment it as such), or add the request-level 3 s soft check.

## Resolution (2026-09-20)

1. **Fixed.** `ResearchEngine.research()` now accepts `keywords: list[str] | None = None`
   (`tutor/retrieval/research.py`), threads it into `_process_archive`, and appends the
   tokenized keywords to the lexical query terms used for candidate generation (spec
   §7.2 step 1). Added `tests/test_review_fixes.py::test_research_accepts_keywords_kwarg`,
   `test_research_tool_run_research_real_engine` (drives `research_tool.run_research`
   against a real `ResearchEngine`, not a fake), and a signature-introspection contract
   test (`test_research_keywords_contract_matches_callers`) asserting every kwarg the app
   layer passes is a real accepted parameter, to prevent this regressing silently again.

2. **Fixed.** `tutor/tools/schemas.py`'s `validate_tool_call` now rejects `keywords` with
   more than 3 items, any item longer than 40 characters (after stripping), or any
   empty/whitespace-only item, and normalizes accepted keywords by stripping whitespace.
   The JSON schema (`RESEARCH_TOOL`) now also declares `maxItems: 3` and
   `items.maxLength: 40` so the constraint is visible to the model, not just enforced
   server-side.

3. **Fixed.** Added an `RLock` to `ZimWorker` guarding `start`/`request`/
   `_terminate_child`/`close` end-to-end (held for the whole `request()` call, including
   the `poll` wait), so overlapping requests from multiple threads on one worker can no
   longer race on `self._process`/`self._conn`. Added `ZimWorker.interrupt()` (kill the
   current child without permanently closing the worker) and updated
   `research.py::_call_worker` to call it — and briefly join the abandoned thread — when
   its outer wait times out, instead of silently dropping a thread that may still hold
   the worker. Verified via
   `tests/test_review_fixes.py::test_zim_worker_survives_concurrent_timeout_and_normal_requests`
   (mixed short-deadline and normal-deadline requests hammered from 6 threads), run 3x
   locally with no flakes, plus the existing `tests/test_zim_worker.py` suite.

4. **Fixed.** `_TOP_N_ARTICLES` changed from 8 to 6 (spec §7.2 step 4: "Top 6 articles
   (cap 10)") and exposed as the `top_n_articles` constructor knob on `ResearchEngine`,
   clamped to the spec's cap of 10 regardless of the caller-supplied value ("spec wins on
   caps").

5. **Fixed.** Added a distinct `_DEFAULT_SOFT_DEADLINE_S = 3.0` and a `soft_deadline_s`
   constructor/call parameter on `ResearchEngine`, independent from
   `_PER_OP_DEADLINE_CAP_S` (which remains the per-archive-op cap). `research()` now
   checks the request-level soft deadline before consulting each further archive; once
   it has elapsed, remaining archives are skipped and the response is returned with
   whatever passages are already packed, marked `status="partial"`. The hard deadline
   (default 8 s) is unchanged and still governs worker kill/restart. Existing
   `tests/test_research.py::test_deadline_never_raises_and_returns_partial_or_empty`
   remains green (the join added for finding 3 is capped at 0.5 s and only runs after a
   successful `interrupt()`, so it does not blow the test's timing budget).

Lower-severity items (`_READ_CHUNK = 1` byte-at-a-time streaming, calc sandbox review,
dev-machine config paths) were reviewed as informational/already-fine in the original
document and are **not fixed** here — they were not ranked medium-or-above findings and
are out of scope for this pass.
